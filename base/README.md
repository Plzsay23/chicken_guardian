# base — 주행·하위 제어

## 상태
- `chicken_base` ROS 2 패키지 작성 완료, colcon build 성공.
- `base_node`: `/cmd_vel` 구독, `/odom`·`/imu/data_raw`·`/battery` 발행 — 실행/토픽 발행 확인됨 (배터리 14.6V, 정지 IMU az≈9.88 m/s²).
- `teleop_keyboard`: **hold-to-move 방식으로 교체 완료 (2026-10-08)** — QWE(전진+아크턴)/ASD(제자리 회전)/ZXC(후진+아크턴)/R,F(속도). 키 누르고 있는 동안만 이동, 떼면 즉시 정지. 실주행 검증됨. 이전의 "누르면 유지" 방식 `teleop_keyboard.py`와 임시 `teleop_keyboard_test.py`는 이걸로 대체되어 제거됨.
- 속도 명령 프레임(11바이트/XOR)은 **이 로봇 실물로 검증 완료** (바퀴 띄운 상태, `base_node`를 통해 `/cmd_vel`로 vx=0.1 지속 송신, 아래 "알아낸 것" 참고).
- **리모컨-PC 우선순위 확인 완료: 리모컨이 PC보다 우선권을 가짐** (아래 참고).

## 실행 방법
```bash
cd ~/chicken && source install/setup.bash
ros2 run chicken_base base_node                 # 또는: ros2 launch chicken_base base.launch.py
ros2 run chicken_base teleop_keyboard            # 다른 터미널, 바퀴 확인 후에만
ros2 service call /set_light std_srvs/srv/SetBool "{data: true}"   # 라이트 켜기 (false=끄기). base.launch.py 가 light_node 도 띄움
python3 ~/chicken/base/tools/light.py blink      # ROS 없이 시험 (light_node 와 동시에 쓰지 말 것)
```
키: W/S 전후진, Q/E 전진하며 좌/우 회전(아크), A/D 제자리 좌/우 회전, Z/C 후진하며 좌/우 회전, R/F 속도 업/다운. 전부 **누르고 있는 동안만 이동**.
파라미터는 `config/params.yaml` (port, baud, max_vx/vy/wz, cmd_timeout_s 등) — 하드코딩 없음.

**주의**: `base_node`는 한 번에 하나만 띄울 것 — 같은 `/dev/base`에 두 프로세스가 동시에 쓰면 명령 프레임이 섞일 수 있음 (직접 겪음, 중복 실행 발견 후 정리함).

## 발행/구독
- 서비스: `/reset_odom` (`std_srvs/srv/Trigger`) — odom x/y/theta를 (0,0,0)으로 즉시 리셋. `base_node` 재시작 없이 호출 가능: `ros2 service call /reset_odom std_srvs/srv/Trigger {}`
- light_node: 구독 `/light`(std_msgs/Bool), 서비스 `/set_light`(std_srvs/SetBool), 발행 `/light/state`(latched). GPIO 40핀 BOARD 7번(params pin)
- 발행: `/odom`(20Hz, odom→base_link 메시지만, TF 미발행 — EKF와 중복 방지), `/imu/data_raw`(20Hz), `/battery`(20Hz)
- 구독: `/cmd_vel` — `../INTERFACES.md` 참고

## 알아낸 것
- **covariance 값 채움 (2026-10-08)**: `/odom` twist(vx=6.4e-4 ← std 0.0254 m/s 실측[vx=0.15 주행 중], vy=1e-6 ← 이 섀시는 옆으로 못 움직여서 사실상 0, 수치안정용 placeholder, wz=4e-4 ← std 0.02 rad/s 실측[wz=0.3 주행 중]), `/imu/data_raw`의 angular_velocity_covariance(1.6e-7 ← 정지 시 자이로 σ≈0.0004 rad/s), linear_acceleration_covariance(1.21e-4 ← 정지 시 가속도 σ≈0.011 m/s²) 전부 실측 기반으로 채움. `base_node.py`의 `diag6`/`diag3` 헬퍼로 대각선만 채우고 비대각은 0.
- `/dev/base` = udev 고정 심볼릭링크(`99-chicken-serial.rules`, 시리얼 `5C8D079806`) → 실제로는 `/dev/ttyACM0`. **이 보드는 "PC"와 "ROS" 라벨의 USB-C 포트 2개가 있고, 둘 다 같은 WCH 칩(1a86:55d4)이지만 시리얼번호가 다르다. 속도 명령은 "ROS" 포트에서만 먹힌다 (PC 포트는 텔레메트리만 나오고 명령은 완전 무시함, 다른 보드로 확인됨).** `/dev/base`가 가리키는 시리얼번호(`5C8D079806`)가 바로 그 "ROS" 포트라서 현재 배선은 올바름.
- `MODE="0666"` udev 규칙 덕분에 **dialout 그룹 추가 불필요** — `chicken` 계정으로 바로 포트 열림 확인함.
- 텔레메트리 프레임(24바이트)은 이전 기록과 동일: `7B | stop u8 | vx vy wz i16 | ax ay az i16 | gx gy gz i16 | 전압 u16(mV) | XOR | 7D`. 가속도 ÷1671.84(≈16384 LSB/g와 동일), 자이로 ×0.00026644(≈65.5 LSB/(°/s)와 동일) — 이전 추정치와 일치 확인.
- **명령 프레임 검증됨** — `7B 00 00 | vx vy wz i16 | XOR(앞 9바이트) | 7D`, 11바이트.
  - 다른 동일 기종 M500 보드(랩탑, 2026-10-07): vx=+0.1 → 전진, vx=-0.1 → 후진, wz=+0.3 → 반시계(CCW, 위에서 봄) — REP-103 그대로, 부호 반전 불필요.
  - **이 로봇(Jetson, 2026-10-08, 바퀴 띄운 상태)에서도 `chicken_base`로 재검증함**: `base_node` + `teleop_keyboard`로 WASD 조작 정상 동작.
- **리모컨(FlySky i-BUS) vs PC 명령 우선순위 — 확인됨 (2026-10-08, 바퀴 띄운 상태)**: `base_node`를 통해 vx=+0.1(전진)을 `ros2 topic pub -r 10`으로 계속 송신하는 중에, 리모컨으로 후진 스틱을 주니 **실제로 후진함 — 리모컨이 PC 명령을 이김**. 즉 이 펌웨어는 리모컨 입력이 들어오면 PC 속도 명령보다 우선 적용하는 것으로 보임 (정확한 내부 로직은 미확인이나, 동작 결과는 명확). **이건 안전상 좋은 소식** — 테스트 중 문제가 생기면 리모컨 스틱을 조작해서 PC 명령을 덮어쓰고 제어를 되찾을 수 있다는 뜻.
  - **PC 복귀 조건 확인됨 (2026-10-08, 바퀴 띄운 상태)**: PC가 전진(vx=0.1)을 계속 보내는 중 —
    - 리모컨 스틱을 **중립으로 되돌리면 약 3초 후** PC 명령(전진)으로 복귀함 (즉시 아님, 지연 있음).
    - **리모컨 전원을 끄면** (스틱이 후진 위치인 채로 끔) **1.5~2초간 후진이 계속되다가 정지**, 그 후 약 3초 뒤에 PC 명령(전진)으로 복귀함.
    - **⚠️ 안전 주의**: 리모컨 전원 차단은 스틱 위치와 무관하게 즉시 정지시키는 비상정지가 아님. 스틱이 중립이 아닌 상태에서 전원을 끄면 수신기 페일세이프 지연으로 1.5~2초간 그 동작이 그대로 유지됨. **리모컨으로 비상정지할 때는 전원을 끄기 전에 반드시 스틱을 먼저 중립으로 돌릴 것.** 진짜 즉시 정지가 필요하면 로봇 자체의 전원 차단이 더 확실함.
    - PC 복귀까지 공통적으로 약 3초 지연이 있음 — 펌웨어의 리모컨↔PC 전환 히스테리시스로 추정 (정확한 내부 로직 미확인).
- `chicken_base` 패키지 구조: `ament_python`, 실행 파일 `base_node`/`teleop_keyboard`, `protocol.py`에 프레임 인코딩/디코딩 공통 로직 분리.
- `/odom`은 보드가 pose를 안 주기 때문에 vx/vy/wz를 직접 적분한 dead-reckoning — covariance는 실측 기반으로 채움(위 "covariance 값 채움" 참고).
- **제자리 회전 시 고무 스크럽 마찰음 큼 — 하드웨어 특성, 소프트웨어 문제 아님 (2026-10-08, 바퀴 띄운 상태 wz=+0.3 지속 테스트)**: 4바퀴 모두 좌우 반대방향으로 정상 회전하는 것 확인(소프트웨어/프로토콜 정상). 다만 이 섀시가 조향 기구 없는 강체 4륜 스키드 스티어 방식이라, 제자리 회전 시 4바퀴 전부가 옆으로 미끄러져야 해서 고무 스크럽 마찰음이 크게 남 — 탱크/스키드스티어 로더와 같은 원리. 회전이 "잘 안 먹히는" 느낌과 "뒷축 기준으로 도는 것처럼 보이는" 현상도 이 마찰 저항 + M500의 Pendulum Suspension(뒤쪽 흔들림 서스펜션)으로 인한 앞/뒤 접지력 차이로 추정 — **명령 프로토콜(vx/wz)이나 base_node 쪽 버그 아님**, 고치려면 섀시 자체를 바꿔야 함. 참고용으로만 기록, 액션 아이템 아님.

## 오돔 정확도 검증 (2026-10-08, 바닥 주행)

- `base_node` 재시작으로 `/odom`을 (0,0,0)으로 초기화 후, vx=0.15 m/s로 2초간 전진 명령.
- **odom 계산 거리: x=13.59cm (y≈0, 깔끔한 직진).**
- **실측 이동 거리: 13.6~13.8cm.**
- **일치함 (오차 1mm 수준) — dead-reckoning 직진 거리 추정 정확도 검증 완료.**
- 참고: 명령×시간 이론값(0.15×2=30cm)보다 odom 값이 작게 나온 건 가속 램프업/퍼블리셔 시작 지연 때문으로 추정 — 실제 이동 거리 자체는 odom과 일치하므로 odom 적분 로직 자체는 정상.
- 주의: 이 테스트 전, 이전 회전(wz) 테스트들로 인해 odom heading이 틀어진 상태에서 먼저 시도했다가 x/y가 섞여 나온 적 있음 → `base_node`를 재시작해서 odom을 리셋해야 깨끗한 비교 가능. (영구적으로는 odom 리셋 서비스나 `/reset_odom` 같은 기능을 추가하면 편리할 수 있음 — 다음 할 일 참고.)

## wz 명령-피드백 비율 스윕 테스트 (2026-10-08, 바퀴 띄운 상태)

wz=0.3/0.5/0.7/1.0 각각 2초씩 명령, 정상상태(초반 ramp 구간 제외) 피드백 평균:

| 명령 wz (rad/s) | 실측 평균 wz | 비율 |
|---|---|---|
| 0.3 (별도 4초 테스트) | ~0.145 | ~48% |
| 0.5 | 0.2157 | 43% |
| 0.7 | 0.2931 | 42% |
| 1.0 | 0.4214 | 42% |

**발견**: 비율이 명령값 전 구간(0.3~1.0)에서 42~48%로 거의 일정함. 만약 고무 스크럽 마찰에 의한 포화(토크 한계)였다면 명령값이 커질수록 비율이 더 떨어지거나 특정 절대값에서 평평해질(plateau) 것으로 예상되는데, 그렇지 않고 **비율이 일정하다는 건 오히려 스케일/캘리브레이션 계수 문제일 가능성을 시사함** (마찰 효과를 완전히 배제하는 건 아니지만, 지금 데이터만으론 스케일 문제 쪽에 더 무게가 실림). 정확한 원인은 미확인.

**실용적 시사점**: 이 로봇에서 실제로 원하는 회전 속도 R을 얻으려면, 지금은 명령값으로 R/0.43 ≈ R×2.3 정도를 보내야 함. 네비게이션/텔레옵 쪽에서 참고하거나, `base_node`에 보정 계수를 넣는 걸 고려할 수 있음 (단, 안전 한도 `max_wz`를 넘지 않는 선에서).

## wz 보정계수 적용 (2026-10-08)

위 스윕 테스트를 1.5~3.0까지 확장한 결과, **비율이 10배 범위(0.3~3.0) 내내 41.9~48%로 거의 일정** — 토크/마찰 포화라면 높은 값에서 비율이 떨어져야 하는데 그렇지 않음 → **선형 스케일 문제로 결론**.

`protocol.py`의 `build_cmd_frame()`에 `WZ_COMPENSATION = 1/0.434 ≈ 2.304`를 적용: wz 인코딩 전에 이 계수를 곱해서 보정. **vx/vy는 보정 안 함** (이미 정확함을 오돔 테스트로 확인).

보정 후 재검증 (max_wz=0.5로 재시작):
| 요청 wz | 실측 wz | 비율 |
|---|---|---|
| 0.3 | 0.320 | 106.5% |
| 0.5 | 0.477 | 95.4% |

**거의 정확히 1:1로 교정됨.** 이제 `/cmd_vel`에 wz를 보내면 실제 rad/s와 거의 일치함 — 네비게이션/텔레옵 쪽에서 더 이상 별도 보정 계산 불필요.

주의: `base_node`가 `on_cmd_vel`에서 `max_wz`로 클램핑하는 건 **보정 적용 전(사용자가 요청한 real-world wz)** 기준이고, `build_cmd_frame` 내부에서만 인코딩 직전에 보정 곱셈이 들어감 — 안전 캡의 의미가 바뀌지 않음.

## 자이로 축/스케일 검증 (2026-10-08, 보드 고정 후, 바닥 주행)

제어보드를 섀시에 고정(나사 2개, 뒤쪽)한 뒤, `/odom`의 theta가 π/2(90°)에 도달할 때까지 wz=+0.3 명령, 동시에 `/imu/data_raw`의 angular_velocity.z를 독립적으로 시간 적분.

- **odom 적분 각도: 92.3°**
- **자이로(IMU) 독립 적분 각도: 87.9°**
- **실제 회전: 약 90° (육안 눈대중 확인, 정밀 측정 아님 — 각도계/바닥 마킹 등으로 정밀 측정하면 더 좋음)**

양쪽 다 눈대중 90°에 근접(오차 3% 이내로 추정), 서로도 일치함 → **자이로 축 방향·스케일(0.00026644), wz 보정 적용 후 odom 회전 추정 모두 대략적으로 타당해 보임.** 단, 기준값 자체가 정밀 측정이 아니라서 정확한 오차율은 아직 모름 — 더 정밀한 검증은 다음 할 일로 남김.
